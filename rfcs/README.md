- [RFC-0041](RFC-0041-external-identity-providers.md) — External Identity Providers: Keycloak, a Realm per Tenant, and the Way Out (Accepted 2026-09-22 — all seven decisions taken; K3 manages realms through the admin API, K4 is a per-tenant policy, K7 brings self-registration and 2FA into v1. Both measurements DONE 2026-09-22 against Keycloak 26.7.4 — the sub survives export+import unchanged, the admin API does what K3 needs, and a realm export carries the client secret and the password hashes, so it is a secret. BUILD STEPS 2, 3 and 5 BUILT 2026-09-23 in reference 0.1.120/0.1.121, `oaap.core.identity` 0.5.0 and `oaap.core.tenant` 0.7: Keycloak as an ordinary OAAP app pinned to 26.7.4, a provider object that is a URL and says nothing about where the server runs, the OIDC login in identity (a second way to ESTABLISH a session, not a third way to resolve one — so nothing downstream changed), the binding to (provider, subject, tenant) and to nothing else, and the first-login policy whose switch only the operator may move. STEP 4 BUILT the same day in 0.1.122 and `oaap.core.tenant` 0.8: OAAP creates the realm and the client itself, built on Jörg's direction as a CONNECTOR CONTRACT rather than a Keycloak integration — four verbs, one table per product, so a second SSO product is a file and a row. Two rules run rather than being promised: nothing deletes, and nothing is created before the version has been checked. The measuring found two of K3's own requirements in tension — a credential narrow enough for K3.4 cannot read the version K3.1 wants pinned, so where OAAP cannot read it a human states it and every surface says the number was STATED, not read (§5.3). Measured end to end on oaap-test. Open: STEP 6 BUILT the same day in 0.1.123 and `oaap.core.tenant` 0.9: the connector's fifth verb moves the two switches inside the space (self-registration, second factor) and records what the space ANSWERED, never what it was told — an instruction that did not take stays visible as a disagreement instead of being tidied away by its own failure. Because the registration page belongs to the realm, the dangerous pair of K7 is now refused when the SPACE is open whatever the record says. Measured end to end: a person registered themselves and arrived with no rights. The measuring also killed a rule that could never have fired — Keycloak answers `acr=1` to a password login, so a second factor is read from `amr` and never from silence (§5.4). STEP 7 BUILT the same day in 0.1.124 and `oaap.core.tenant` 1.0: a club can leave the node it is on -- the connector's sixth verb exports the realm, a tenant archive now carries the tenant's own record, and an EMPTY node adopts one, refusing by name every collision it finds rather than merging. The measuring changed the design twice and corrected this RFC itself. Two of the three doors to a realm export write a file that looks perfect and holds NO people, and neither fails -- so the file is counted against the space and thrown away on a difference. An IMPORTED realm has no administrator, because Keycloak gives that to whoever created a realm, so the move needs one act by a person on the new node. And §5.0's conclusion that no re-binding is needed was half a conclusion: K4 binds to a PAIR, §5.0 measured only the subject, and the issuer is the address of a node -- the very thing a move changes. Without a re-point every member would have arrived as a stranger with their roles gone. Measured on a real move of a tenant from oaap-test to oaap-demo (§5.5). Open: step 8 oaapx01, which needs Jörg's explicit go-ahead)
